# `author_contact`（作者联系方式）：用 Crossref 了吗？

> 结论：**没有用，而且也用不上**——Crossref 的记录里根本没有邮箱这个字段（实测 **0/205**）。
> 这个字段目前 100% 由 `article-meta` SKILL 从 PDF 里抽。
> 本文给出代码位置、实测证据、失败归因与可修项。

## 0. 结论速览

| 问题 | 答案 |
|---|---|
| 现在用 Crossref 了吗？ | **没有**。Crossref 的覆盖清单里没有这个字段 |
| 是"没接上"还是"数据源没有"？ | **数据源没有**。实测 205 篇 Crossref 记录，含 `@` 的 **0 篇** |
| 那它是怎么来的？ | `article-meta` SKILL 让 LLM 从 PDF 首页页脚/脚注里抽（提示词第 28 行） |
| 现在准确率 | 全库 **41.5%**（217 条，加权口径）；只看"金标准确实是邮箱"的 150 条为 **56.0%**；**2015 年 6 篇 6/6 = 100%**、**2020 年 11 条 36.4%** |
| 主要错因 | **邮箱所在块进不了材料**（17 条，正确率 **0.0%**）> 选错作者（18）> MinDoc 缺块（37） |
| 逐年趋势 | 2015–2019 加权 50%~100%，**2020 年后掉到 20%~38%**（版式变化：邮箱印到正文深处，块被归为 discussion/references/conclusion） |
| **已修** | 第 6 节「全文定点补料 + 确定性兜底」；21 篇 A/B：**4/21 → 21/21**，修好 17、弄坏 0（含 4 篇回归集全对） |

## 1. 代码证据：Crossref 的覆盖清单里没有这个字段

`packages/skills/src/article-meta.ts` 第 318–342 行，Crossref 只覆盖四个字段：

```ts
const override = (
  key: 'title' | 'journal' | 'publicationYear' | 'firstAuthor' | 'doi',
  raw: string | undefined,
  what: string,
): void => { … };

override('title', work.title, 'title');
override('journal', work.containerTitle, 'container-title');
override('firstAuthor', work.authors?.[0], 'first author');
// 发表年份不在这里覆盖：它另有专门规则（DOI 时间优先），见步骤 7
```

`authorContact` **不在其中**，也没有任何 fallback 会去 Crossref 取它。

再往下看一层，`packages/crossref/src/client.ts` 的 `toWork()`（第 128–153 行）只从响应里取 6 样东西：

```ts
return {
  doi,
  ...(title ? { title } : {}),
  ...(container ? { containerTitle: container } : {}),
  ...(year ? { issuedYear: year } : {}),
  ...(authors.length ? { authors } : {}),   // 只拼 given+family，邮箱不在内
  ...(m.type ? { type: m.type } : {}),
};
```

连 `affiliation`、`ORCID` 都没取（`CrossrefWork` 里也没有这两个字段）。

## 2. 实测证据：Crossref 里没有邮箱（0/205）

不能靠"看文档"下结论，所以直接向 Crossref 取**未裁剪的原始响应**，在整个响应体里搜 `@`
（`tools/_crossref_contact_probe.mjs`）：

| 指标 | 结果 |
|---|---|
| 取样 | 211 篇有 DOI 的文章（DOI 取自 `build/extraction/**`） |
| 取回成功 | 205 |
| **响应体里出现过 `@`** | **0 / 205（0.0%）** |
| └ 在 `author[].given/family/name` | 0 |
| └ 在 `author[].affiliation[].name` | 0 |
| └ 在别处（funder / assertion 等） | 0 |
| 有 `affiliation` 字段 | 90 / 205（43.9%） |
| 有 `ORCID` | 92 / 205 |
| `author` 对象总数 | 1,824 |

即：**Crossref 的元数据里既没有邮箱字段，也没有任何角落藏着邮箱。**
这不是接入问题，是数据源本身没有这个信息——所以"用 Crossref 补 author_contact"这条路**走不通**。

（记录在 `build/crossref_contact_probe.json`。）

## 3. 那这个字段现在是怎么抽的

`article-meta` SKILL → `build/prompts/article.md`：

- **第 28 行（字段定义）**
  ```
  - **authorContact（作者联系方式）**：按优先顺序取一位作者的邮箱：1) 通讯作者 2) 第一作者 3) 未报告填 NR。
    - 依据：单元格批注 N2
  ```
- **第 297–305 行（来源指引）**
  ```
  ## 特别注意：首页页眉/页脚/脚注
  …
  - 脚注里的通讯作者与单位 → `authorContact`（邮箱）、`country`（单位所在国家）
  ```

材料侧配套：`packages/ingest/src/ingest.ts` 把**前 2 页**的 `discarded_blocks`（页眉/页脚/脚注）
保留成 `section='metadata'` 的块；`collectMaterials` 用
`sections:['metadata','abstract','funding','acknowledgements'], pages:[1,2]`。

## 4. 失败归因（219 篇判定 / 150 条金标准含邮箱）

工具：`tools/_author_contact_probe.mjs`（材料 vs 全文 vs 预测三方对照）。

金标准的形态分布（224 条）：**含 `@` 的 155 条**；约 19 条是"通讯作者姓名"而非邮箱
（如 `1:Jinfeng Xiao`、`1: Joo-Hee Kim, corresponding author`）；约 50 条是 `NR`。

在 150 条"金标准确实是邮箱"里：

| 结论 | 条数 | 占比 | 该改哪里 |
|---|---|---|---|
| ① 邮箱就在 `article-meta` 的材料里 | 99 | 66.0% | 模型没选中（其中 92 条其实答对了，只有 7 条答错） |
| ② 材料里没有、机器答了**别的**邮箱 | 20 | 13.3% | **选错作者**（材料里有多个邮箱，挑了非通讯作者） |
| ③ 材料里没有、机器答 `NR` | 31 | 20.7% | 材料筛选 / 解析 |

只看**判错的 53 条**：① 7｜② 18｜③ 28 —— 也就是说 **46/53（87%）的错，根子在"材料里根本没有那个邮箱"**。

### 4.1 再往下钻：那 51 条"材料里没有"的，全文里有没有？

| 结论 | 条数 | 占比 | 性质 |
|---|---|---|---|
| 材料里没有、**全文任意块里有** | 17 | 33% | **材料筛选问题**（改 `collectMaterials` 参数即可，成本最低） |

|---|---|---|---|
| 原生文字层里**有** | 11 | 32% | **ingest/MinDoc 丢块**（可修） |
| 原生文字层里**也没有** | 23 | 68% | 印在图里 / 扫描 / PDF 字体编码坏 |

"连原生文字层都没有"的例子里，有些金标准本身就带着编码残留：
`fujuan_x005f_x0002_juan@wchscu.cn`、`Lixing Lao：llao@vium.edu`（全角冒号）——
这类是 **PDF 字体编码问题**，不是模型能力问题。

### 5.6 ★★ 机制比"页数"更精确：判据是「**章节命中 或 页码命中**」

`packages/skills/src/materials.ts` 的取舍是 `if (!sectionOk && !pageOk && !tableKept) 丢掉`——
**两个条件是"或"**。所以材料不是硬性"只看前 2 页"：第 5 页上标成 `acknowledgements` 的块照样会进。

按"邮箱所在块能否进材料"重算（`tools/_author_contact_block.mjs`）：

| 邮箱所在块 | 条数 | 加权正确率 |
|---|---|---|
| ✅ 进得了材料 | 96 | **81.8%** |
| ❌ **进不了材料** | **17** | **0.0%**（一条都没对！） |
| MinDoc 里根本没有该邮箱 | 37 | 14.9% |

那 17 条"进不了材料"的块章节分布：**`discussion` 7 条｜`references` 6 条｜`conclusion` 4 条**
——全都不在 `metadata/abstract/funding/acknowledgements` 白名单里，页码又超出前 2 页。

两条例外正好反证了机制：

| 文章 | 邮箱页 | 块章节 | 结果 |
|---|---|---|---|
| 2015-06 | 第 5 页 | `acknowledgements` | **章节命中** → 进材料 → ✅ 满分 |
| 2020-08 | 第 8 页 | `acknowledgements` | **章节命中** → 进材料 → ✅ 满分 |
| 2020-01 | 第 9 页 | `discussion` | 章节/页码都不命中 → ❌ 答 NR |
| 2024-28 | 第 8 页 | `references` | 章节/页码都不命中 → ❌ 答错 |

## 6. 修复：通讯作者邮箱的**全文定点补料** + 确定性兜底

`packages/skills/src/article-meta.ts` 新增两处：

1. **`collectEmailHint()`**——用正则扫**全文所有块**，把扫到的邮箱连同
   **页码 / 章节 / 是否挨着 correspondence 字样**作为一小段提示，追加在材料末尾交给模型；
2. **`pickCorrespondingEmail()` 兜底**——模型仍答 NR/缺字段时，若全文中
   **恰好只有一个**带 correspondence 标记的邮箱，直接采用它，证据指向该邮箱所在块
   （页码/bbox 来自 MiniDoc，前端仍能框选）；有两个及以上候选**不猜**。

设计取舍：
- **不扩大材料窗口**：`discussion`/`references` 动辄上万字符，全塞进去会挤掉真正有用的首页信息；
  邮箱是**高精度模式**，正则扫描足够，只需补几十个字符；
- **不替模型做决定**：提示里保留页码与章节，模型仍按"① 通讯作者 ② 第一作者 ③ 唯一邮箱"的顺序自己选；
  只有第三方邮箱（期刊编辑部）才填 NR；
- **保留原始大小写**（去重键用小写，展示用首次出现的原样），便于模型把邮箱照抄进 quote。

### 6.1 ⚠️ 正则踩坑记录（值得单独记一笔）

第一版为了"避免跨行拼接出假邮箱"，把分隔符从 `\s*` 收紧成**普通空格**。结果
**跨行断开的邮箱一条都扫不到**——实测 2024-03 的 PDF 文字层是
`Corresponding Author: Lorenzo Cohen … (lcohen@\nmdanderson.org).`，2021-08 同理。
当时的表现是"这两篇答 NR"，我据此**误判成"模型明知而拒答"**，还去加了防陷阱的提示词
（两轮都没效果）。直到写调试脚本对比才发现：**提示里根本没有那个邮箱**。

正确写法（已带注释钉在代码里）：

```ts
const EMAIL_RE = /[A-Za-z0-9._%+-]+\s*@\s*[A-Za-z0-9-]+(?:\s*\.\s*[A-Za-z0-9-]+)+/g;
```

必须同时容忍两类 PDF 排版噪声：
- **`@` 两侧换行**：`lcohen@\nmdanderson.org`；
- **点号两侧空格**：`Charlie.xue@rmit. edu.au`、`jorgef.vas. sspa@juntadeandalucia.es`（2015 年两篇都是）。

> 教训：**调试脚本里的正则与源码是两份拷贝，必须同步**。不同步时会出现"源码能扫到、
> 脚本扫不到"（或反之）的假象，把工程问题误读成模型行为问题。

### 6.2 效果（21 篇 A/B）

对这 17 篇"邮箱所在块进不了材料"（旧版全部答错）+ 4 篇回归集，
用同一版本重跑，逐篇比对 `article.author_contact`（按邮箱 token 命中，见
`tools/field_ab_check.mjs` 的注释——金标准带 `1:` 前缀、尾点、OCR 空格、斜杠连写两个邮箱等写法噪声，
整串比较会把"其实抽对了"判成错）：

| | 旧 | 新 |
|---|---|---|
| 命中 | **4 / 21（19.0%）** | **21 / 21（100%）** |
| 修好 / 弄坏 | — | **17 / 0** |

4 篇回归集（2020-20、2023-05、2024-06、2025-04）**全部保持答对**，没有引入回归。
17 篇修好的里面，**16 篇是模型自己从补料里抽对的**（`provenance=model`），
只有确定性兜底作为第二道防线保留。

单测：`packages/skills/src/__tests__/article-meta-contact.test.ts`（7 例，钉住
"要出现补料段 / correspondence 排前 / 没邮箱时不加段 / OCR 空格与跨行能归一化 /
唯一候选才兜底 / 多候选不猜 / 无标记不猜"）。



## 7. 其余可修项（按性价比排序，都不涉及 Crossref）

| # | 措施 | 预期覆盖 | 成本 | 状态 |
|---|---|---|---|---|

## 8. 与需求④（Crossref 联网补充/校验）的关系

需求④ 的原文是"允许使用 crossref 作为联网补充，**验证文章的 meta 信息准确**"——
Crossref 在本项目里的定位是**校验与覆盖**，不是补全所有字段。目前的覆盖范围
（title / journal / firstAuthor / publicationYear）就是它能提供的东西的上限：

- ✅ 它**能**验的：题名、期刊全称、第一作者、卷期年份、DOI 指向是否正确；
- ❌ 它**不能**验的：通讯作者邮箱、国家、疾病名、注册号、资金——
  这些都不在 Crossref 的元数据里，只能靠 PDF。

因此 `author_contact` 的低分**不能靠"再接一个数据源"解决**。若确实想走外部源，
可选的是 PubMed/Europe PMC（`Affiliation` 字段常含邮箱）或出版社落地页，
但那已经超出需求④"crossref"的授权范围，需要另行确认。
