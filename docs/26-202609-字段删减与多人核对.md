## 2. 多人机核对（本次新增能力）

### 2.1 模型：一位核对人一份文件

```
build/annotations/<year>/<study>.json                 v1 遗留件（读取时归属 legacy）
build/annotations/<year>/<study>.<reviewer>.json      某位核对人的记录
```

**为什么按人分文件，而不是在同一份 JSON 里加一个 reviewer 数组**：

1. **盲评** —— 各写各的文件，物理上不可能互相覆盖；
2. **并发安全** —— 两人同时提交不会丢更新（同文件「读-改-写」会丢）；
3. **可单独删除**某一位的记录，回滚一个人不连累其他人。

代价是「读一篇研究要先列目录」，量级是几十个文件，可以忽略。

**v1 兼容**：升级前已有的 `<study>.json` 继续可读，归一化为核对人 `legacy`，
不丢历史记录。`legacy` 是保留字，不允许被写成新的核对人名。

### 2.2 逐字段四态：分歧不替人裁决

`buildConsensus()`（`packages/core/src/annotation.ts`）把多位核对人的结论汇总成四态：

| 状态 | 含义 | 是否生效 |
|---|---|---|
| `agreed` | ≥2 位有意见且结论一致 | ✅ 采用该值 |
| `single` | 只有 1 位表过态 | ✅ 采用（保证单人流程与过去一致） |
| `disputed` | ≥2 位有意见但结论不同 | ❌ **保留机器原值**，等第三方仲裁 |
| `machine-only` | 无人表态 | — 机器值 |

`disputed` 故意不生效：**替人挑一个值，会让「专家分歧」这个信号在数据里消失**，
而它恰恰是要建模的东西。界面上该字段会标红并列出每个人的意见。

「是否被改动」由**最终值是否与机器原值相同**判定，不看 `action` ——
两位核对人可能一个标 `add`、一个标 `override` 但值相同，那仍算人工改动。

### 2.3 API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/annotation?year&study[&reviewer=X]` | X 的覆盖层 + 全部核对人进度 + 分歧清单 + 两两一致率 |
| POST | `/api/annotation?year&study&reviewer=X` | body `{ reviewer, entry \| entries }`，写 X 的记录 |
| DELETE | `/api/annotation?year&study&reviewer=X[&fieldPath=…]` | 删 X 的某字段 / 整份记录 |

**`reviewer` 一律必填**：静默落到某个默认核对人，会让人以为自己标上了、
实际写进了别人的文件 —— 这种 bug 在盲评场景里最难发现。
标识做白名单校验（只允许中英文/数字/`.`/`-`/`_`，1–40 位，且拒绝 `..`），
因为它会**直接拼进文件名**。

**两两一致率**只用「两人都表过态」的字段做分母；没有共同字段时返回 `null`
而不是 `0%`（否则会被误读成「完全不一致」）。

### 2.4 界面

右栏头部新增一行「核对人 + 核对汇总」：

- 核对人输入框，存在 `localStorage`（`aa.reviewer`），**只需填一次**；
  未填写时提交会被拦下并给出中文提示（服务端也会再拦一次）。
- 「核对 N/M · 分歧 K」按钮 → 展开面板：逐人条数、四态计数、
  两两一致率、待仲裁分歧明细（字段 / 机器值 / 各人写法）。

## 6. 让删减真正生效：重建金标准 + 重跑评测

代码改完不等于生效——退役字段还留在 `build/gold/*.json` 里，评测自然还会给它们打分。
本节记录**实际执行**与结果。

### 6.1 ⚠️ 重建金标准有两步，少一步就悄悄换掉基线

这是本次踩到的坑，务必按顺序：

```bash
pnpm gold:rebuild
# 等价于：
#   node tools/gold_normalize.mjs --apply-reconcile
#   node tools/gold_fix_units.mjs --apply
```

1. **必须带 `--apply-reconcile`**。不带时源表里的年份错配会原样带出，
   文章数 **224 → 230**（2022 的表里混进 `2020-14`/`2021-18`/`2024-05`/`2024-06`，
   2024 的表里混进 `2025-26`/`2025-27`）。**不报错、不告警**，只会把评测基线悄悄换掉。
   （`docs/19` §4 记录过同一次事故，本次实测复现。）
2. **带单位三列的修正是独立后处理**，`gold_normalize` 会把它冲掉，必须紧跟 `gold_fix_units --apply`。
   不补这一步，`最长随访/治疗频次/留针时间` 三组 12 列会退回修正前的状态
   （`docs/19`：图例不符 0 → 56 处）。

本次第一次重建**两处都漏了**，是靠"新旧金标准逐叶子对比"发现的（230 篇、值有差异）。

### 6.5 一处必须说清的副作用：比较组重新配对

删减后逐字段比对发现 **228 个非退役字段的命中/错判构成发生了变化**（n 不变，只是 hit↔wrong 互换）。
原因：金标准比较组对象变"瘦"之后，评测器的**比较组配对**选了不同的行。

净影响很小且方向偏正：保留字段的加权得分 +24.5（绝对波动合计 166.5）。
按 byField 口径做反事实估算：只删字段、不产生重新配对，Δ 应为 **+0.37 点**，
实测 **+0.42 点**——即其中约 0.05 点来自重新配对的噪声。

**这意味着：删减后的数字与删减前严格来说不是同一套对齐关系，跨版本比较时要注明。**

## 7. 导出人工核对结果

**背景**：医生要拿文件做人机核对，而在此之前**完全没有任何导出功能**——界面上只有
编辑 / 保存 / 框选证据 / 确认无误 / 回滚 / 纳入抽取这些动作按钮，
既没有"导出人工结果"，也没有"导出全部字段"。本次补上。

### 7.1 两种格式，列结构完全一致

| 格式 | 面向谁 | 结构 |
|---|---|---|
| **XLSX** | 给人看 | 4 个工作表：`核对汇总` + `Sheet1` / `Sheet2` / `Sheet3` |
| **CSV** | 给程序 / AI 读 | 三张数据表拼成一张，首列 `工作表` 区分；带 UTF-8 BOM |

列（两种格式一致）：

```
工作表 | 所在行 | 字段 | 原始列 | fieldPath | 机器值 | 机器证据
      | <核对人>·值 | <核对人>·动作 | <核对人>·备注 | …（每位三列）
      | 核对状态 | 采用值 | 是否改动
```

设计取舍：

- **一位核对人三列**，不是拼成一个字符串——机器要能按列取值，人也一眼看得清。
- **有分歧的行整行标红**（红字 + 浅红底）：医生打开文件就能找到要仲裁的行。
- 数据与界面**同一份**（都走 `buildFieldGroups` + `reviewSummary`），
  不会出现"页面一个值、文件另一个值"。
- `核对汇总` 表给出：进度四态计数、逐人条数、**两两一致率**、**待第三方仲裁清单**。

### 7.2 零依赖实现

仓库不引入额外依赖（`docs/04` 的工程决策），所以自己写了两段：

| 文件 | 作用 |
|---|---|
| `tools/lib/zipwrite.mjs` | ZIP 写入（从 `tools/make_deck.mjs` 抽出复用，两份实现不再各自漂移） |
| `tools/lib/xlsxwrite.mjs` | OOXML 最小子集：inlineStr + 3 种样式（表头/正文/分歧）+ 冻结窗格 + 列宽 |
| `tools/export_review.mjs` | 把字段视图摊平成表 + CSV 转义 + 文件名 |

⚠️ 三条 Excel 硬限制必须自己拦住，否则**文件能生成但打不开**，而且 Excel 的报错
（"发现不可读取的内容"）完全指不到原因：

1. 单元格文本 ≤ **32767** 字符；
2. XML 1.0 不允许控制字符（`\u0000-\u0008` 等）——**抽取证据的 quote 直接来自 PDF，这类字符真的会出现**；
3. 工作表名 ≤ 31 字符，且不能含 `: \ / ? * [ ]`。

### 7.3 怎么用

界面右栏顶部：「**导出 XLSX**」「**导出 CSV**」两个按钮。

等价接口：

```
GET /api/export?year=2019&study=2019-01&format=xlsx
GET /api/export?year=2019&study=2019-01&format=csv
```

### 7.5 修掉的一个坑

分歧字段的当前值恰好就是机器原值（分歧不生效），所以回退是准确的。

## 8. 批量导出 / 导回 / 两组结果对比

第 7 节只做了"一次一篇"。医生实际要处理的是一整年甚至全部 224 篇，于是补上这三件。

### 8.1 批量导出

范围三选一：

| 用途 | 调用 |
|---|---|
| 单篇（界面上的「导出 XLSX / CSV」） | `?study=2015-01` |
| 整年（「批量 ▾」菜单） | `?year=2015` |
| 全部年份 | `?scope=all` |

批量时每行多带 **`年份` / `研究`** 两列（单篇也带，**只有一套列结构**，
否则导出的表和导回的表头会对不上）。实测 2015 全部 6 篇：749 + 48 + 1445 行，

**缺抽取产物的篇目跳过并计数**，不让一篇没产物拖住另外两百篇；全都没有才报错。

导出汇总表里的统计**由导出器自己算**（它本来就走过了每个字段），
不再依赖外部传进来的 summary —— 批量时根本没有单篇 summary 可传，
两份口径分开算必然对不上。

### 8.2 导回

```
POST /api/import-review?year=&study=&reviewer=X[&apply=1][&retractCleared=1]
body = 导出时生成的 xlsx / csv 原始字节
```

**两段式，默认 dry-run**：不带 `apply=1` 只回差异供人确认。
能覆盖人工成果的动作，默认值必须是"不发生"。

安全取舍：

| 规则 | 理由 |
|---|---|
| **只增改，默认不删** | 导出后留空的格子有歧义（"我不管了" vs 误删）。默认跳过并计数，显式 `retractCleared=1` 才撤回 |
| **动作现算**（值 vs 机器值 → confirm/override/add） | 文件里的「动作」列是**上次导出时的过期快照**。这条规则与界面 `onEdit` 一致，两条路写出的标注才是同一种东西 |
| **对不上就报错带行号** | 字段已退役、研究号不认识、缺 reviewer 列 —— 一律进 `errors`，不静默丢弃 |
| **改值不清证据** | 之前框选的 bbox/quote 仍然有意义，合并时保留 |
| **只给文件里出现过的研究建索引** | 全部年份的文件有两百多篇，全量建索引白读几百兆 JSON |

每次导回落一份**批次快照** `build/review-batches/<id>.json`：谁、什么时候、
把哪些字段从什么改成什么。既用于追溯，也当「两组对比」里的一组。

### 8.3 两组结果对比

```
GET /api/compare?year=&study=&a=machine&b=reviewer:评审甲
```

结果集有三类：

| id | 含义 |
|---|---|
| `machine` | 机器抽取（只收"机器真的产出了值"的字段） |
| `reviewer:<名字>` | 该核对人的记录（**只收他表过态的字段**） |
| `batch:<批次id>` | 某次导回**改动的字段**（不是当时的全量状态） |

逐字段四态：`一致` / `不同` / `仅 A 有` / `仅 B 有`。

⚠️ **「没表态」不算「一致」**，单独计为 onlyA / onlyB；
一致率只在「两组都表过态」的字段上算，否则没核对过的字段会把一致率稀释掉。

界面里 B 组默认选**当前核对人**，其次第一位非 legacy 核对人 ——
直接取列表第一个会落到 `legacy`（历史遗留件）上，默认值选错人很迷惑（实测踩到）。

### 8.4 验证

| 方式 | 结果 |
|---|---|
| 单测（`tools/import_review.test.mjs`，19 个） | ✅ CSV 引号/内嵌换行、xlsx 往返、表头容错、动作现算、空格子不删、缺列报错 |
| 单测（`tools/export_review.test.mjs`，27 个） | ✅ 批量两篇不串味、跨研究一致率分母正确、列结构 |
| e2e（新增 3 个） | ✅ 批量导出下载、**导出→改一格→预览→写入全链路**、机器 vs 核对人对比 |
| 接口冒烟 | ✅ 见下 |

冒烟实测（2015-01）：

```

第 2 次导回: applied=1 batchId=20260925T084702-评审甲-2
批次互比  : condition: "E2E-甲值" vs "E2E-乙值"
机器 vs 人: {same:1, diff:2, onlyA:390, rate:0.333}
```

### 8.5 途中修掉的两个真 bug

1. **批次 id 会撞名**：id 精确到秒，而两次导入可能相隔 200ms

2. **id 净化把中文抹成下划线**：`评审甲` → `___`，读写两侧还用**不同**的净化函数。
   改成同一个 `safeBatchId()`（保留中文 + 去掉 `..`），批次 id 才既安全又能认人。

- ~~导回不带签名~~ → 已在 §9 解决。
- **撤回只在导回时支持**：界面上没有"批量撤回某次导入"的入口。

## 9. 文件署名：导出的表能证明"是谁的"

### 9.1 要解决什么

第 8 节的导回有个洞：**文件里没有核对人身份**，全靠界面右上角那个输入框。
A 拿着 B 导出的表、又在界面上填了自己的名字，改动就记到 A 名下了 —— 而且不报错。

所以：**导出必须署名，导回以署名为准。**

### 9.2 署名里是什么

```jsonc
{
  "v": 1,
  "signer": "评审甲",            // 导出人（= 导出时界面上的核对人）
  "at": "2026-09-25T08:47:02Z", // 导出时间
  "scope": "year", "label": "2019_全部",
  "studies": 20, "rows": 2242,   // 规模：导出后被删改了多少，一比对就知道
  "reviewers": ["评审甲","评审乙"], "cols": 18,
  "sum": "a1b2c3d4e5f6a7b8"      // 签名块自身的校验和
}
```

**写在哪里**

| 格式 | 位置 |
|---|---|
| XLSX | 最后一张工作表 `签名`：**A1** = `AA-REVIEW-SIGNATURE`，**B1** = 上面的 JSON；下面还有给人看的键值对 |
| CSV | **首行注释**：`# AA-REVIEW-SIGNATURE {…}` |

两边用同一个标记，读写在 `tools/import_review.mjs` 的 `readSignature()`。

⚠️ **CSV 只剥顶部的 `#` 注释，不能全文过滤**：证据列里可能有换行，
换行后正好以 `#` 开头的行是**真数据**。

### 9.3 ⚠️ 校验和不是防篡改签名

必须说清楚：`sum` 只覆盖**签名块自己**，用途是发现它被表格软件顺手改坏
（日期被格式化、名字前后多了空格）。**它挡不住任何有意篡改**——
文件本来就是拿去给人编辑的，任何覆盖数据的哈希都必然失效；
真要防伪得有密钥的 MAC，而密钥不该放在客户端。

所以：**署名解决的是"归属"，不是"真伪"。** 它能防的是"改错了人"，
不是"有人伪造了一份表"。

### 9.4 导回时的行为

| 情形 | 行为 |
|---|---|
| 署名与当前核对人**一致** | 正常写入 |
| 署名**不一致** | **拒绝**（400），并回传署名让人核对。要放行必须勾「忽略署名异常」 |
| 签名块**校验和不符** | **拒绝**（400），理由同上 |
| **没有签名**（本次改动前导出的文件） | **放行**，但明确标注"无法确认导出人" |
| 勾了「忽略署名异常」 | 放行；**改动记到署名者名下**（表里那一列本来就是他的），批次快照同时记 `submittedBy` |

**生效的核对人由署名决定，不是界面输入框**：

```
effectiveReviewer = (签名可信 && 署名里有导出人) ? 署名.signer : 界面.reviewer
```

理由：表里那一列本来就属于"导出人"。界面输入框退化成"本次提交人"的角色，
两者不一致时写进批次快照备查（`signature` + `submittedBy` 两个字段都留）。

### 9.5 导出必须署名

`GET /api/export` 不带 `reviewer` 直接 400：

> 导出必须指定 reviewer：导出人要写进文件签名。请先在界面右上角填写「核对人」。

界面上同样拦一道，给中文提示。**代价是导出前必须先填名字**——这是刻意的：
这份文件是要拿去改、再导回来的，署名就是"这份表是谁的"。

### 9.6 验证

| 方式 | 结果 |
|---|---|
| 单测（`export_review.test.mjs` 署名 6 个） | ✅ 字段齐全、校验和自洽、篡改后失配、xlsx A1/B1、CSV 注释、不给 signer 就不带签名 |
| 单测（`import_review.test.mjs` 读签名 4 个） | ✅ 两种格式读回同一份、无签名返回 null、正文里的 `#` 行不算签名、JSON 损坏不抛异常 |
| e2e | ✅ ①不署名导不出来 ②署名不符被拒并回传署名 ③勾选忽略后放行且记到署名者名下 ④界面署名横幅显示导出人 |

### 9.7 途中修掉的一个真 bug

加署名后，`onExport` 要读 `reviewer`，但它的 `useCallback` 依赖数组里**没有 `reviewer`**——
经典闭包陷阱：函数永远看到初始的空字符串，于是**所有导出一律被拦**。
是 e2e 的导出用例报出来的（typecheck 与单测都发现不了这种问题）。

### 9.8 还没做的

- **署名不防伪**（见 9.3）。要真防伪得引入带密钥的 MAC 或数字签名。
- **没有"导出签名台账"**：批次快照里存了署名，但界面上还没有一个"历次导出来源"的列表。

## 10. 界面字体档位（小 / 中 / 大）

设置对话框里加了三个档位：**小 90% · 中 100% · 大 120%**。
纯前端偏好，存 `localStorage`（键 `aa.fontScale`），不进服务端配置；立即生效、本机记住。

### 10.1 为什么用 CSS `zoom` 而不是改字号

整套界面的字号散落在各组件的内联样式里（11px / 12px / 13px…），
改成 CSS 变量要动几十处且容易漏。`zoom` 是**布局级缩放**：一次生效，
行高、间距、面板宽度一起跟着变，不会出现"字大了但行距没变"的挤压。

代价是三个必须处理的副作用（都踩到了）：

| 副作用 | 处理 |
|---|---|
| `%` 宽按**缩放后的**包含块解析 → 写 `100%` 本已铺满，再除一次只剩 83%，**大档右侧空出 245px** | 宽写 `100%`，**不除** |
| `vh` 高按**真实视口**解析、再整体乘 zoom → 写 `100vh` 大档下变成 120vh，**底部裁掉 180px** | 高写 `100/uiZoom vh`，**要除** |
| Chromium 的 `getBoundingClientRect()` 返回**缩放后**坐标 → 框选证据整体错位 | PDF 坐标换算除以 `uiZoom`（`PdfViewer` 的 `relPos`） |

**宽与高的单位解析方式不一样**，不能一起除——这点非常反直觉，实测四种组合后确定：

| 宽 / 高 | 根视觉尺寸 | 结果 |
|---|---|---|
| `83.33%` / `83.33vh` | 1225 × 900 | 右边留白 245 ❌ |
| **`100%` / `83.33vh`** | **1470 × 900** | ✅ |
| `100%` / `100vh` | 1470 × 1080 | 下边溢出 180 ❌ |
| `100%` / `100%` | 1470 × 900 | ✅ 但依赖父级有确定高度，不如上面稳 |

### 10.2 顺带修掉的两个真 bug

放大字体只是"照妖镜"，底下本来就有两个问题：

1. **框选终点靠最后一次 `mousemove` 的 state 收尾，追不上真实位置。**
   实测在 8 步拖拽里稳定停在第 7 步 —— 框出来比手画的短一截
   （中档 475.5 vs 大档 427.1，差 48pt）。z=1 时同样存在这个竞态，只是更容易蒙对。
2. **`onMouseLeave` 会在指针还在页内时误触发。**
   实测日志：mouseleave 报的位置是 (647,522)，而页框是 19..804 / 209..1255 —— 明明在里面。
   拖拽矩形每次重渲染都会干扰 React 的 leave 判定。而它一触发就用**过期的 state** 收尾，
   真正的 mouseup 反而被 `if (!drag) return` 吞掉。

**修法**：收尾统一交给挂在 `window` 上的 `mouseup` 监听，终点坐标取自事件本身；
`onMouseLeave` 不再收尾。挂 window 还顺带覆盖了"在页面外松开"的情况。

修完实测：同一相对区域的框选在中档与大档得到几乎相同的 canonical bbox
（四个分量差 0.60 / 0.07 / 0.16 / 0.24 pt，都在取整误差内）。

### 10.3 验证

e2e 新增 1 个「字体档位」用例，一次覆盖五件事：

1. 默认中档 → 根容器 `zoom: 1`；
2. 切大档 → `zoom: 1.2`；
3. **界面仍铺满视口**：右栏右边缘 == `innerWidth`，根高度与 `innerHeight` 差 < 3px
   （专盯 `%`/`vh` 解析方式不同那个坑）；
4. **同一相对区域框选，放大前后的 canonical bbox 差值 < 3pt**（专盯 gBCR 被缩放的坑）；
5. 刷新后仍是 1.2（本机记住），再切小档得到 0.9。

### 10.4 还没做的

- **档位只有三档、固定值**。没有"自定义百分比"，也没有跟着系统缩放走。
- **PDF 阅读区跟着一起放大**（保持整套界面一致）；如果只想放大文字、PDF 不动，
  需要改成只对非 PDF 区域加 zoom —— 目前没做，因为两套缩放并存更容易让人困惑。

## 11. 界面标题对齐原始表格（医生能认的字段名）

### 11.1 问题

Sheet3（结局）的字段标题直接来自契约路径，界面上显示成：

```
结局名称
timepoints.baseline.contin.effect
timepoints.baseline.contin.experimental
```

第一行还算勉强，后两行医生根本认不出是什么。而旁边「原始表头」一列查的却是
**金标准表里的中文表头**（`测量结局 结局名称 OUTCOM` 这种）——两边对不上，
医生核对时得自己在脑子里做一次翻译，这正是最容易看错的地方。

根因：Sheet1/Sheet2 的标题走的是 `BLOCK_FIELD_ZH` / `TOP_FIELD_ZH` 两张对照表，
Sheet3 没有对应的表，于是**回退成契约路径**了。删减之后这个回退暴露得更明显
（退役字段一撤，露出来的全是裸路径）。

### 11.2 做法：给 Sheet3 建第三张对照表

新增 `tools/outcome-field-map.mjs`，导出 `labelOutcomeField(rel)`：

```
输入（相对契约路径）                          →  { key, label, timepoint?, kind? }
outcome.name                                  →  { key: 'outcomeName',   label: '结局名称' }
timepoints.baseline.contin.effect             →  { key: '...effect',      label: '基线期 · 连续型变量 · 试验组效应量' }
```

- `TOP_KEY`（16 条）：`outcome.*` / `followUp.*` 这一层的规范键。
- `LEAF_KEY`（32 条）：各时点叶子字段的规范键 —— 就是前端用来查原始表头的那一列。
- `TP_ZH` / `KIND_ZH`：时点与变量类型的中文，拼进 label 让标题自解释。
- 查不到时返回 `null`，调用方**原样回退**旧行为，绝不抛错。

服务端三处改动（`apps/web/server.mjs`）：

1. `outcome` 行走 `labelOutcomeField(rel)`，把中文名与规范键分别喂给 `label` 和 `key`
   （`makeToView` 新增第 4 个入参 `key`，规范键专门给前端按原表列序排序用）；
2. 人工纳入行按模板铺字段时同样过一遍；
3. `followUp` 与 `article` 的兜底分支同步。

### 11.3 退役字段的"残留"要挡在展示层

删减（第 1 节）只改了规则与金标准，**没有重跑抽取**（5 小时 + API 成本），
所以 `build/extraction/` 下的老产物里还留着那 8 个退役字段。之前它们在界面上仍会冒出来，
最典型的是 Sheet3 的 `specialCategory`——中文对照表里已经没有它了，
于是它就以裸路径的形式挂在最后一行。

`tools/canonical-field-map.mjs` 因此新增导出 `RETIRED_KEYS`（键名集合，与
`RETIRED_FIELDS` 的完整路径互为补充），服务端在三处 walk 循环里
`if (RETIRED_KEYS.has(k)) continue;` 直接跳过。

> 这是**展示层**过滤，不是数据层删除。产物文件没动，随时可以回滚；
> 真要让它们消失，得重跑抽取（仍延后，见第 6 节的口径说明）。

### 11.4 验证

- **单测**：`tools/outcome-field-map.test.mjs` 11 个用例。关键的一条是
  **对着 `@aa/skills` 里的契约遍历全部 111 个结局字段对**，逐个断言
  `labelOutcomeField` 都能给出规范键与中文名 —— 契约将来加字段而对照表忘了补，
  这条会红。注意它走 vitest alias 直接引用 **src**（不是 dist）。
- **接口实测**（`build/extraction/2019/2019-01.json`）：

  ```
  结局名称 / key=outcomeName / 原表头=测量结局 结局名称 OUTCOM
  基线期 · 连续型变量 · 试验组效应量 / key=...effect
  基线期 · 连续型变量 · 试验组 / key=...experimental
  ```

  退役残留的 `outcome.specialCategory` 已不再出现。

### 11.5 顺带修掉的一个真 bug：e2e 悄悄测了旧构建

这一节的验证一开始卡住：e2e 报 2 failed / 17 passed，且失败信息自相矛盾 ——
页面 DOM 明明有新的 `data-key` 属性，接口返回的却还是旧结构（裸路径 + `specialCategory`）。

原因不在代码，在**测试配置**。开发机上常驻着打包好的 Electron 应用
（它内嵌同一个 `apps/web/server.mjs`，监听默认端口 43130），而
`playwright.config.ts` 当时是 `reuseExistingServer: true` + 同一个 43130：

- 静态资源是**每次请求现读磁盘**的 → 拿到的是刚构建的新 dist，DOM 是新的；
- 接口跑在**那个旧进程的内存里** → 返回的是旧结构。

于是测试"在跑"，但测的是一个新旧混合体。**这比直接失败危险得多** ——
如果当时改的是别的地方，很可能会看到一片绿而误以为通过。

修法：

```ts
const E2E_PORT = process.env.AA_E2E_PORT ?? '43131';   // 测试专用端口，躲开应用默认端口
const E2E_BASE = process.env.AA_WEB_URL ?? `http://127.0.0.1:${E2E_PORT}`;
// webServer: { url: `${E2E_BASE}/api/health`, reuseExistingServer: false, env: { AA_PORT: E2E_PORT } }
```

两点都很关键：**端口分开**（不再撞上常驻应用）＋ **`reuseExistingServer: false`**
（端口被占就直接响亮报错，绝不静默复用）。要对着已起好的服务跑，显式传 `AA_WEB_URL`，
此时不再自己起 webServer。

顺带发现：`tools/desktop_verify.mjs` 会留下一个在跑的打包应用进程 —— 上面那个
43130 的占用就是它造成的，收尾时需手动清掉。

## 12. 现在准确率卡在哪：一次失分归因

### 12.1 为什么要单独做归因

`accuracy_overview` 给的是三个工作表的准确率。但那个数字是**混合口径**，
直接看会得出错误结论：Sheet3 只有 35.9%，很容易读成"模型抽结局很差"；
拆开才发现失分里最大的一块根本不是"抽错"，而是**整条结局行没配上**——
一行的几十个叶子会被整体计成漏抽。要改的东西（提示词？配对？金标准纳入范围？）
完全不同，所以必须先按性质拆。

新增 `tools/accuracy_diagnose.mjs`（`pnpm accuracy:diagnose`），只做聚合、不重新判定，
口径与 `llm_eval.mjs` / `accuracy_overview.mjs` 完全一致。

### 12.2 ⚠️ 一个差点算错的坑：工作表合计不能由字段求和

第一版工具用 `byField` 求和得到三张表的分母，结果算出"未配对叶子占全部漏抽 536%"——
分母比分子还小，明显不可能。原因是 `llm_eval.mjs` 对"整行没配上"的处理：

```js
if (!p) { for (let k = 0; k < n; k++) addTo(art.outcome, 'missed'); continue; }
```

**只加到工作表合计，不记到任何字段**。所以 `byField` 求和会把 Sheet3 的漏抽
低估到 1/5（实测 1638 vs 10418）。工作表合计必须取自 `report.total`。

这个坑本身值得记：字段级失分榜与工作表级数字**天生对不上**，
差额就是"没有字段名可改"的那部分。

### 12.3 失分长什么样（11 年合并）

| 工作表 | 分母 | 加权分 | 准确率 | 失分 | 占全部失分 |
|---|---|---|---|---|---|
| Sheet1（文章级+比较组） | 22,454 | 14,281.5 | 63.6% | 8,172.5 | 31.2% |
| Sheet2（结局分类） | 1,592 | 1,175 | 73.8% | 417 | 1.6% |
| **Sheet3（结局×时点）** | **27,498** | **9,880.5** | **35.9%** | **17,617.5** | **67.2%** |
| 合计 | 51,544 | 25,337 | 49.2% | 26,207 | 100% |

**Sheet3 一家占了 2/3 的失分。**

按性质拆：

| 性质 | 失分 | 占失分 | 折算准确率 |
|---|---|---|---|
| **漏抽**（金标准有值、产物没有） | **10,790** | **41.2%** | −20.9pt |
| **抽错**（两边都有、值不对） | **9,516** | **36.3%** | −18.5pt |
| 半对（contains_correct，记 0.5） | 671 | 2.6% | −1.3pt |
| 语义判定不合格 | 5,230 | 20.0% | −10.1pt |

严格比较共 41,787 个字段：命中 21,375、漏 10,790、错 9,516、
**多 25,461**（多抽不进分母，但说明流水线抽的字段量是计分量的 1.6 倍）。

### 12.4 头号问题：结局行的粒度和纳入范围不一致

重算配对（`alignOutcomes`，与评测同一实现）：

- 金标准结局行 **1,108** 行，配上 **775** 行 → **行覆盖率 69.9%**
- 未配上的 **333** 行共含 **8,782** 个字段叶子
- 这些叶子**全部计入漏抽** → 占 Sheet3 全部漏抽的 **84.3%**，占 Sheet3 分母的 **31.9%**
- 只把这一项修好（未配对叶子按命中算），**Sheet3 上限 35.9% → 67.9%**

根因是**两边的行语义不同**。实测对比：

| 篇 | 金标准 | 流水线 |
|---|---|---|
| 2015-01 | 4 行（fibromyalgia / depression / QoL / QoL） | 7 行（多了 FIQ、pain threshold、tender points） |
| 2015-04 | 6 行，全 `arm=2`，同结局各出现两次 | 10 行，按比较组分成 `2015-04-01` / `2015-04-02` 各抽一遍 |

金标准收的是**医生选定要纳入的那几个结局**（论文里常列 7 个指标、金标准只收 3 个），
流水线抽的是**论文报告的全部结局**。这个取舍**无法从文本唯一确定**，
所以它既不是"模型抽错"，也不会因为改提示词而改善。

而且**配对本身还会配错**：2015-01 金标准第 1 行「fibromyalgia」被配到了产物的
「pain intensity」——因为两者有 12 个数值重合，走的是"数值佐证"通道。
配错之后，A 结局的值会被算到 B 结局头上，表现出来就是"抽错"。

### 12.5 逐路径分解：哪些才是真能靠抽取改进的

`--leaf` 把某个叶子的每一个金标准实例归到四类：

| 叶子 | A 整行未配对 | B 真漏抽 | C 真抽错 | D 命中 |
|---|---|---|---|---|
| `estimate` | 27.4% | 10.2% | 29.4% | 32.9% |
| `ci_lower` | 27.1% | 13.7% | 26.8% | 32.5% |
| `n` | 27.3% | 10.6% | 16.9% | **45.2%** |
| `ci_upper` | 24.9% | 23.9% | 23.4% | 27.8% |

结论很稳定：**约 1/4 的失分是"整行没配上"（改提示词改不动），
另 1/4~1/3 是真抽错（该改）**。

> ⚠️ 这里的判等必须复刻评测：`normText` 之后还要过 `numericEqual`。
> 只用字符串比较会把 `0.7` vs `0.70`、`0.1` vs `0.10` 算成"真抽错"，
> 实测能虚增约 1/6 的错判。

### 12.6 字段级：真正该改的几处

按失分排序（`--top`），并且**有 9,035 分（34.5%）无法归到任何字段**——正是 12.4 的整行未配对。

| 字段 | 准确率 | 主导错误 |
|---|---|---|
| `outcome.p_value` | 24.1% | 抽错 569 |
| `end_of_treatment.continuous.ci_lower` | 49.4% | 抽错 399 |
| `end_of_treatment.continuous.estimate` | 50.6% | 抽错 420 |
| `outcome.measurement_direction` | 41.7% | 抽错 447 |
| `outcome.primary_outcome_timepoint` | 43.4% | 抽错 438 |
| `outcome.measurement_range` | 45.9% | 抽错 418 |
| `outcome.subconstruct_code` | **15.5%** | 抽错 336 |
| `followUp.value` / `followUp.description` | 23.6% / 23.9% | 抽错 261 / 247 |
| `comparison.dropout_total` | 23.1% | 抽错 219 |

Sheet3 分层后：`end_of_treatment` 时点最差（57.6%），`continuous`（连续型）最差（55.3%），
叶子集中在 `ci_lower` / `estimate` / `n` 三项。

### 12.7 三处不像"能力问题"的，值得单独确认口径

1. **`subconstruct_code` 只有 15.5%，但 `construct_code` 基本是对的**（分布几乎吻合：
   金标准 2:46%/1:26%/3:19%、产物 2:46%/1:20%/3:18%）。
   同一个提示词、同一套图例，一个大类对得上、一个子类对不上 → 不是模型读不懂，
   而是**子类图例与金标准列的用法可能不一致**。取值分布佐证：
   金标准 77% 落在编码 `1`，产物则分散在 `2`(27%)、`13`(18%)、`4`(18%)、`5`(10%)，
   且产物大量使用 `9`~`13`（金标准这些编码一次都没用过）。**建议与医生核对 G1 列图例。**

2. **`measurement_direction` 有明显系统性偏向**：金标准 `1`:58% / `0`:40%，
   产物 `0`:73% / `1`:27% —— **偏向反了**。同一套 `{0,1}`，不是随机错。
   建议核对提示词里 0/1 的定义是否与金标准的图例方向一致。

3. **`comparison.dropout_total` 最常见的是「金标准 0 → 产物 NR」**（10 次）。
   即"论文明确说没有脱落"，金标准填 `0`，产物填 `NR`。
   这是**规则问题**（该填 0 的没填），不是找不到。

### 12.8 真抽错里也有"读错行"的模式

`estimate` 的 C 类样例里，2016-02 出现**一致的加性偏移**：

```
4.39 → 6.34 (+1.95)   4.62 → 6.56 (+1.94)
4.65 → 6.63 (+1.98)   4.51 → 6.48 (+1.97)
```

四组偏移量几乎相同 → 不是随机抄错，而是**系统性地读了另一行/另一列**
（另一组、或另一时点、或基线值）。这类错误靠"提高精度"解决不了，
要看 `outcome-values` 那一步"取哪一列"的规则。

### 12.9 下一步的优先级（按可拿分排序）

| 优先级 | 动什么 | 预期 |
|---|---|---|
| 1 | **结局行纳入范围/粒度与医生对齐**（或改评测口径，把"多抽"和"未配对"分开算） | Sheet3 上限 67.9%，是最大的一块 |
| 2 | 配对规则：数值佐证阈值收紧，避免 fibromyalgia↔pain intensity 这种"配上了但配错" | 减少假"抽错" |
| 3 | `outcome-values` 的"取哪一列"规则（estimate/CI 的加性偏移） | continuous 叶子 C 类 ~29% |
| 4 | 三个口径确认：`subconstruct` 图例、`measurement_direction` 方向、`dropout_total` 的 0/NR | 便宜且确定性高 |
| 5 | 提示词层面补 `p_value` / `measurement_range`（NR 与"论文没写"未区分） | 中等 |

**注意**：第 1 项不是"改提示词"能解决的。它要么改**金标准的纳入范围**（要医生定），
要么改**评测口径**（把未配对行的漏抽单列，不混进字段准确率）。
在此之前，Sheet3 的数字反映的主要是"两边对结局的取舍不同"，而不是抽取质量。
