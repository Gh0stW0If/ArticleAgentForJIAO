## 2. 多人机核对（本次新增能力）

### 2.1 模型：一位核对人一份文件

```
build/annotations/<year>/<study>.json                 v1 遗留件（读取时归属 legacy）
build/annotations/<year>/<study>.<reviewer>.json      某位核对人的记录
```

**为什么按人分文件，而不是在同一份 JSON 里加一个 reviewer 数组**：

1. **盲评** —— 各写各的文件，物理上不可能互相覆盖；
2. **并发安全** —— 两人同时提交不会丢更新（同文件「读-改-写」会丢）；
3. **可单独删除**某一位的记录，回滚一个人不连累其他人。

代价是「读一篇研究要先列目录」，量级是几十个文件，可以忽略。

**v1 兼容**：升级前已有的 `<study>.json` 继续可读，归一化为核对人 `legacy`，
不丢历史记录。`legacy` 是保留字，不允许被写成新的核对人名。

### 2.2 逐字段四态：分歧不替人裁决

`buildConsensus()`（`packages/core/src/annotation.ts`）把多位核对人的结论汇总成四态：

| 状态 | 含义 | 是否生效 |
|---|---|---|
| `agreed` | ≥2 位有意见且结论一致 | ✅ 采用该值 |
| `single` | 只有 1 位表过态 | ✅ 采用（保证单人流程与过去一致） |
| `disputed` | ≥2 位有意见但结论不同 | ❌ **保留机器原值**，等第三方仲裁 |
| `machine-only` | 无人表态 | — 机器值 |

`disputed` 故意不生效：**替人挑一个值，会让「专家分歧」这个信号在数据里消失**，
而它恰恰是要建模的东西。界面上该字段会标红并列出每个人的意见。

「是否被改动」由**最终值是否与机器原值相同**判定，不看 `action` ——
两位核对人可能一个标 `add`、一个标 `override` 但值相同，那仍算人工改动。

### 2.3 API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/annotation?year&study[&reviewer=X]` | X 的覆盖层 + 全部核对人进度 + 分歧清单 + 两两一致率 |
| POST | `/api/annotation?year&study&reviewer=X` | body `{ reviewer, entry \| entries }`，写 X 的记录 |
| DELETE | `/api/annotation?year&study&reviewer=X[&fieldPath=…]` | 删 X 的某字段 / 整份记录 |

**`reviewer` 一律必填**：静默落到某个默认核对人，会让人以为自己标上了、
实际写进了别人的文件 —— 这种 bug 在盲评场景里最难发现。
标识做白名单校验（只允许中英文/数字/`.`/`-`/`_`，1–40 位，且拒绝 `..`），
因为它会**直接拼进文件名**。

**两两一致率**只用「两人都表过态」的字段做分母；没有共同字段时返回 `null`
而不是 `0%`（否则会被误读成「完全不一致」）。

### 2.4 界面

右栏头部新增一行「核对人 + 核对汇总」：

- 核对人输入框，存在 `localStorage`（`aa.reviewer`），**只需填一次**；
  未填写时提交会被拦下并给出中文提示（服务端也会再拦一次）。
- 「核对 N/M · 分歧 K」按钮 → 展开面板：逐人条数、四态计数、
  两两一致率、待仲裁分歧明细（字段 / 机器值 / 各人写法）。

## 6. 让删减真正生效：重建金标准 + 重跑评测

代码改完不等于生效——退役字段还留在 `build/gold/*.json` 里，评测自然还会给它们打分。
本节记录**实际执行**与结果。

### 6.1 ⚠️ 重建金标准有两步，少一步就悄悄换掉基线

这是本次踩到的坑，务必按顺序：

```bash
pnpm gold:rebuild
# 等价于：
#   node tools/gold_normalize.mjs --apply-reconcile
#   node tools/gold_fix_units.mjs --apply
```

1. **必须带 `--apply-reconcile`**。不带时源表里的年份错配会原样带出，
   文章数 **224 → 230**（2022 的表里混进 `2020-14`/`2021-18`/`2024-05`/`2024-06`，
   2024 的表里混进 `2025-26`/`2025-27`）。**不报错、不告警**，只会把评测基线悄悄换掉。
   （`docs/19` §4 记录过同一次事故，本次实测复现。）
2. **带单位三列的修正是独立后处理**，`gold_normalize` 会把它冲掉，必须紧跟 `gold_fix_units --apply`。
   不补这一步，`最长随访/治疗频次/留针时间` 三组 12 列会退回修正前的状态
   （`docs/19`：图例不符 0 → 56 处）。

本次第一次重建**两处都漏了**，是靠"新旧金标准逐叶子对比"发现的（230 篇、值有差异）。

### 6.5 一处必须说清的副作用：比较组重新配对

删减后逐字段比对发现 **228 个非退役字段的命中/错判构成发生了变化**（n 不变，只是 hit↔wrong 互换）。
原因：金标准比较组对象变"瘦"之后，评测器的**比较组配对**选了不同的行。

净影响很小且方向偏正：保留字段的加权得分 +24.5（绝对波动合计 166.5）。
按 byField 口径做反事实估算：只删字段、不产生重新配对，Δ 应为 **+0.37 点**，
实测 **+0.42 点**——即其中约 0.05 点来自重新配对的噪声。

**这意味着：删减后的数字与删减前严格来说不是同一套对齐关系，跨版本比较时要注明。**

## 7. 导出人工核对结果

**背景**：医生要拿文件做人机核对，而在此之前**完全没有任何导出功能**——界面上只有
编辑 / 保存 / 框选证据 / 确认无误 / 回滚 / 纳入抽取这些动作按钮，
既没有"导出人工结果"，也没有"导出全部字段"。本次补上。

### 7.1 两种格式，列结构完全一致

| 格式 | 面向谁 | 结构 |
|---|---|---|
| **XLSX** | 给人看 | 4 个工作表：`核对汇总` + `Sheet1` / `Sheet2` / `Sheet3` |
| **CSV** | 给程序 / AI 读 | 三张数据表拼成一张，首列 `工作表` 区分；带 UTF-8 BOM |

列（两种格式一致）：

```
工作表 | 所在行 | 字段 | 原始列 | fieldPath | 机器值 | 机器证据
      | <核对人>·值 | <核对人>·动作 | <核对人>·备注 | …（每位三列）
      | 核对状态 | 采用值 | 是否改动
```

设计取舍：

- **一位核对人三列**，不是拼成一个字符串——机器要能按列取值，人也一眼看得清。
- **有分歧的行整行标红**（红字 + 浅红底）：医生打开文件就能找到要仲裁的行。
- 数据与界面**同一份**（都走 `buildFieldGroups` + `reviewSummary`），
  不会出现"页面一个值、文件另一个值"。
- `核对汇总` 表给出：进度四态计数、逐人条数、**两两一致率**、**待第三方仲裁清单**。

### 7.2 零依赖实现

仓库不引入额外依赖（`docs/04` 的工程决策），所以自己写了两段：

| 文件 | 作用 |
|---|---|
| `tools/lib/zipwrite.mjs` | ZIP 写入（从 `tools/make_deck.mjs` 抽出复用，两份实现不再各自漂移） |
| `tools/lib/xlsxwrite.mjs` | OOXML 最小子集：inlineStr + 3 种样式（表头/正文/分歧）+ 冻结窗格 + 列宽 |
| `tools/export_review.mjs` | 把字段视图摊平成表 + CSV 转义 + 文件名 |

⚠️ 三条 Excel 硬限制必须自己拦住，否则**文件能生成但打不开**，而且 Excel 的报错
（"发现不可读取的内容"）完全指不到原因：

1. 单元格文本 ≤ **32767** 字符；
2. XML 1.0 不允许控制字符（`\u0000-\u0008` 等）——**抽取证据的 quote 直接来自 PDF，这类字符真的会出现**；
3. 工作表名 ≤ 31 字符，且不能含 `: \ / ? * [ ]`。

### 7.3 怎么用

界面右栏顶部：「**导出 XLSX**」「**导出 CSV**」两个按钮。

等价接口：

```
GET /api/export?year=2019&study=2019-01&format=xlsx
GET /api/export?year=2019&study=2019-01&format=csv
```

| 单测（`tools/export_review.test.mjs`，**21 个**） | ✅ ZIP 往返、XML 转义、控制字符剥离、超长截断、表名净化、分歧/一致/未核对的行内容、CSV 转义、BOM |
| **openpyxl 3.1.5 实读**（`runtime/mineru` 里的严格读取器） | ✅ 4 个工作表名、冻结窗格 `B2`、红色底纹 `FFFDECEA` 全部正确 |
| e2e（`e2e/web.spec.ts`） | ✅ 点按钮真下载：校验 xlsx 是 ZIP（`PK`）、CSV 带 BOM 且含表头 |

顺带把 `tools/` 纳入 vitest（`include` 增加 `tools/**/*.test.mjs`）——
导出器是纯逻辑，没理由只靠 e2e 覆盖。

### 7.5 修掉的一个坑

`核对汇总` 的「待仲裁」表原先取 `reviewSummary().consensus.disputed`，
但那份汇总是在**没有机器值**的前提下算出来的（`buildConsensus({}, …)`），
`machineRaw` 恒为 `null` → 表里显示「机器值：（无）」，会误导仲裁。

改为**从字段视图现取**（那里有真实机器值）。界面上的分歧面板也做了同样的回退：
分歧字段的当前值恰好就是机器原值（分歧不生效），所以回退是准确的。

### 7.6 还没做的

- **导回时不校验"人"**：文件里没有核对人身份，全靠界面上的「核对人」输入框。
  如果 A 拿着 B 导出的表、又在界面填了自己的名字，改动会记到 A 名下。要根治得在导出文件里带一行签名。

## 8. 批量导出 / 导回 / 两组结果对比

第 7 节只做了"一次一篇"。医生实际要处理的是一整年甚至全部 224 篇，于是补上这三件。

### 8.1 批量导出

范围三选一：

| 用途 | 调用 |
|---|---|
| 单篇（界面上的「导出 XLSX / CSV」） | `?study=2015-01` |
| 整年（「批量 ▾」菜单） | `?year=2015` |
| 全部年份 | `?scope=all` |

批量时每行多带 **`年份` / `研究`** 两列（单篇也带，**只有一套列结构**，
否则导出的表和导回的表头会对不上）。实测 2015 全部 6 篇：749 + 48 + 1445 行，

**缺抽取产物的篇目跳过并计数**，不让一篇没产物拖住另外两百篇；全都没有才报错。

导出汇总表里的统计**由导出器自己算**（它本来就走过了每个字段），
不再依赖外部传进来的 summary —— 批量时根本没有单篇 summary 可传，
两份口径分开算必然对不上。

### 8.2 导回

```
POST /api/import-review?year=&study=&reviewer=X[&apply=1][&retractCleared=1]
body = 导出时生成的 xlsx / csv 原始字节
```

**两段式，默认 dry-run**：不带 `apply=1` 只回差异供人确认。
能覆盖人工成果的动作，默认值必须是"不发生"。

安全取舍：

| 规则 | 理由 |
|---|---|
| **只增改，默认不删** | 导出后留空的格子有歧义（"我不管了" vs 误删）。默认跳过并计数，显式 `retractCleared=1` 才撤回 |
| **动作现算**（值 vs 机器值 → confirm/override/add） | 文件里的「动作」列是**上次导出时的过期快照**。这条规则与界面 `onEdit` 一致，两条路写出的标注才是同一种东西 |
| **对不上就报错带行号** | 字段已退役、研究号不认识、缺 reviewer 列 —— 一律进 `errors`，不静默丢弃 |
| **改值不清证据** | 之前框选的 bbox/quote 仍然有意义，合并时保留 |
| **只给文件里出现过的研究建索引** | 全部年份的文件有两百多篇，全量建索引白读几百兆 JSON |

每次导回落一份**批次快照** `build/review-batches/<id>.json`：谁、什么时候、
把哪些字段从什么改成什么。既用于追溯，也当「两组对比」里的一组。

### 8.3 两组结果对比

```
GET /api/compare?year=&study=&a=machine&b=reviewer:评审甲
```

结果集有三类：

| id | 含义 |
|---|---|
| `machine` | 机器抽取（只收"机器真的产出了值"的字段） |
| `reviewer:<名字>` | 该核对人的记录（**只收他表过态的字段**） |
| `batch:<批次id>` | 某次导回**改动的字段**（不是当时的全量状态） |

逐字段四态：`一致` / `不同` / `仅 A 有` / `仅 B 有`。

⚠️ **「没表态」不算「一致」**，单独计为 onlyA / onlyB；
一致率只在「两组都表过态」的字段上算，否则没核对过的字段会把一致率稀释掉。

界面里 B 组默认选**当前核对人**，其次第一位非 legacy 核对人 ——
直接取列表第一个会落到 `legacy`（历史遗留件）上，默认值选错人很迷惑（实测踩到）。

### 8.4 验证

| 方式 | 结果 |
|---|---|
| 单测（`tools/import_review.test.mjs`，19 个） | ✅ CSV 引号/内嵌换行、xlsx 往返、表头容错、动作现算、空格子不删、缺列报错 |
| 单测（`tools/export_review.test.mjs`，27 个） | ✅ 批量两篇不串味、跨研究一致率分母正确、列结构 |
| e2e（新增 3 个） | ✅ 批量导出下载、**导出→改一格→预览→写入全链路**、机器 vs 核对人对比 |
| 接口冒烟 | ✅ 见下 |

### 8.5 途中修掉的两个真 bug

1. **批次 id 会撞名**：id 精确到秒，而两次导入可能相隔 200ms
   （实测就撞了）——撞名 = 后一次**覆盖**前一次的快照，等于悄悄丢一批记录。加了序数兜底。
2. **id 净化把中文抹成下划线**：`评审甲` → `___`，读写两侧还用**不同**的净化函数。
   改成同一个 `safeBatchId()`（保留中文 + 去掉 `..`），批次 id 才既安全又能认人。

### 8.6 还没做的

- **导回不带签名**（见 7.6）：文件里没有核对人身份，全靠界面填的名字。
- **撤回只在导回时支持**：界面上没有"批量撤回某次导入"的入口。
